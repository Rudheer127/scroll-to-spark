# Build rules

These rules apply to every file in this repository. They exist so the code stays easy to read, easy to change and easy to debug by hand.

## The short version

1. No em dashes anywhere in code, comments, strings, commit messages or documents.
2. Search for an existing function or component before writing a new one. Reuse it.
3. One job per file. Small files in a clean tree.
4. Every button and control does something real.
5. Every database table has Row Level Security.

## Reuse before you write

Before adding a helper, hook, component or type:

1. Search `src/lib`, `src/hooks`, `src/components` and the feature folder for something that already does the job.
2. If one exists, use it. If it almost fits, extend it so every caller benefits.
3. If nothing exists, write it once, in the right shared place, with a clear name.
4. Never copy a function into a second file. Two copies means one will be fixed and the other forgotten.
5. A helper used by only one feature lives in that feature. A helper used by two or more features moves to `src/lib` or `src/components/shared`.

## Keep the file tree clean

The layout is defined in [FILE_TREE.md](FILE_TREE.md). The rules that keep it navigable:

- One component per file. The file name matches the component name in kebab-case, for example `thread-card.tsx`.
- Group by feature, not by file type. Everything about comments lives under `src/features/comments`.
- Route files in `src/app` stay thin: they read data, call a feature component and nothing else. No business logic in routes.
- A file over about 200 lines gets split. A function over about 40 lines gets split.
- No file named `utils`, `helpers` or `misc` that collects unrelated code. Name the file after what it does, for example `format-time.ts`.
- No deep nesting past four folders inside a feature.
- When a bug is reported, the folder name alone should tell you where to look. If it does not, rename or move the file.

## Naming

| Thing | Style | Example |
|---|---|---|
| Files and folders | kebab-case | `group-header.tsx` |
| React components | PascalCase | `GroupHeader` |
| Functions and variables | camelCase | `getGroupBySlug` |
| Types and interfaces | PascalCase | `GroupSummary` |
| Constants | UPPER_SNAKE_CASE | `MAX_IMAGE_BYTES` |
| Database tables and columns | snake_case | `group_members` |
| Server Actions | verb first | `createGroup`, `deleteGroup` |

Names say what a thing is or does. No `data2`, `temp`, `thing` or single letters outside short loops.

## TypeScript

- Strict mode on. No `any`. Use `unknown` and narrow it.
- No non-null assertions (`!`) to silence the compiler.
- Types for data come from one place per feature, `types.ts`. Database types are generated by the Supabase CLI and never edited by hand.
- Prefer small explicit return types on exported functions.

## Where code lives

| Kind of code | Location |
|---|---|
| Database reads | `features/<name>/queries.ts` |
| Database writes | `features/<name>/actions.ts` |
| Input checks | `features/<name>/schemas.ts` |
| Screens and pieces of screens | `features/<name>/components/` |
| Supabase client creation | `src/lib/supabase/` only |
| Environment variables | `src/lib/env.ts` only |
| Generic UI pieces (button, dialog) | `src/components/ui/` |
| App frame (sidebar, top bar) | `src/components/layout/` |

Components render. They do not talk to the database and they do not contain business rules. They call a query, an action or a hook.

## What to avoid

- Em dashes. Use a comma, a period, a colon or a hyphen.
- Dead code, commented-out code and unused imports. Delete them. Git remembers.
- `console.log` left in committed code.
- Magic numbers and magic strings. Name them in `src/lib/constants.ts` or the feature's own constants file.
- Deeply nested conditionals. Return early instead.
- Catching an error and doing nothing with it.
- Copy and paste between features.
- Fetching data inside a loop.
- Putting secrets, tokens or keys in code or in a file that is committed.
- Marketing words and filler in code comments. Comments explain why, not what.

## Errors and loading

- Every list and every data screen has three states: loading, empty and error. All three are designed and written.
- Errors shown to a person use plain words and say what to do next. Technical details go to the log, not the screen.
- Server Actions return a result object with `ok`, and either `data` or an `error` message. They do not throw for expected problems such as validation.

## Security

- Every table has Row Level Security turned on in the same migration that creates it. A table without a policy is not allowed to merge.
- Only the owner of a group can delete or edit it. This is enforced by a database policy, not only by hiding a button.
- User input is validated on the server with Zod, even if the form already checked it.
- Image uploads: images only, a fixed size limit in a named constant, and a server check of the file type.
- Third-party API keys are used only in server routes.
- Never trust the browser. Check permissions on the server every time.

## Database

- Every change is a new file in `supabase/migrations`. Never edit a migration that has been applied.
- Every foreign key column has an index.
- Deleting a group removes its threads, comments and memberships through foreign key rules, and this is covered by a test.
- Sample data lives in `supabase/seed.sql` and is clearly labeled as sample content.

## Accessibility

- Every interactive element works with the keyboard and shows a visible focus ring.
- Every image has useful alt text, or empty alt text if it is decorative.
- Color is never the only way to show a state.
- Respect `prefers-reduced-motion`.

## Testing

- A new query, action or schema comes with a Vitest test.
- A flow a person depends on (create, join, leave and delete a group; post a comment with an image; reply in a thread) has a Playwright test.
- A bug fix includes a test that fails without the fix.

## Git and documents

- Small commits with a message that says what changed and why, in plain words. No em dashes.
- Branches are short-lived. Merge through a pull request.
- The only Markdown files in the repository are `README.md` and the four documents in `docs/`. Do not commit plans, notes, scratch files or generated reports as Markdown. Keep those outside the repository.
- Never commit `.env` files, build output, `node_modules` or local tool folders.

## Before opening a pull request

1. Lint, type check and tests pass.
2. Search the diff for em dashes and remove them.
3. Search the diff for new helpers and confirm none duplicates an existing one.
4. Click every button you added or changed and confirm it works.
5. Check the screen at desktop width, and confirm it uses the full width.
